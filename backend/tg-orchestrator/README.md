# tg-orchestrator

Переносимый пакет для оркестрации нескольких **opencode-агентов** (архитектор,
исполнитель, ревьюер) с **Telegram-управлением из РФ**.

Агенты живут в своих opencode-сессиях. Оркестратор будит их, передаёт задачи,
собирает результаты и спрашивает владельца (через Telegram) на важных шагах.
Владелец может писать **любому агенту прямо в Telegram**, а агенты могут
**сами запрашивать апрув** у владельца (кнопки ✅/❌).

```
tg-orchestrator/
├── relay_worker.js          # Cloudflare Worker: прокси Bot API + store-and-forward релей
├── requirements.txt
├── .env.example
├── README.md
├── reports/                 # отдельная папка отчётов агентов (результаты, .md)
└── orchestrator/            # Python-пакет
    ├── __main__.py          # CLI: bot / run / dispatch / send / ask / notify / request ...
    ├── config.py
    ├── notifier.py          # Telegram-бот + доставка + релей агентам
    ├── opencode_client.py   # клиент к opencode Server API
    ├── agents.py            # промпты ролей + диспетчеризация
    ├── core.py              # автомат: architect → executor → owner-gate
    ├── state.py
    ├── agents_registry.json # роль -> id сессии opencode
    └── prompts/
        ├── architect.md     # системный промпт architect
        └── builder.md       # системный промпт executor
```

## 1. Что нужно изменить под свой проект

### 1.1. Cloudflare-воркер (`relay_worker.js`)
Telegram заблокирован в РФ, поэтому весь трафик идёт через Cloudflare Worker:
он проксирует **исходящий** Bot API и принимает **входящие** (вебхук) от
Telegram, складывая апдейты в KV. Локальный бот забирает их по HTTPS
(`GET /pull/<secret>`) — это доступно из РФ без VPN.

1. Создай Worker (`tiny-snowflake` или любой), вставь содержимое `relay_worker.js`.
2. Создай **KV namespace** и привяжи его к воркеру с именем переменной **`RELAY`**
   (обязательно, иначе воркер вернёт 500).
3. Задеплой. Получишь URL вида `https://<your-worker>.workers.dev`.

> В воркере нет секретов — проверка `RELAY_SECRET` убрана. Секретный сегмент
> пути берётся из `.env` (`TELEGRAM_RELAY_SECRET`) и нужен только чтобы скрыть
> эндпоинт от посторонних.

### 1.2. `.env`
Скопируй `.env.example` → `.env` и заполни:

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_CHAT_ID` | твой chat_id (куда присылать уведомления) |
| `TELEGRAM_API_BASE` | `https://<your-worker>.workers.dev/bot` (исходящий прокси) |
| `TELEGRAM_MODE` | `relay` (рекомендуется для РФ) |
| `TELEGRAM_RELAY_BASE` | `https://<your-worker>.workers.dev` |
| `TELEGRAM_RELAY_SECRET` | любая длинная случайная строка |
| `OPENCODE_SERVER_PASSWORD` | пароль opencode Server API (user=`opencode`) |
| `SESSION_ARCHITECT` / `SESSION_EXECUTOR` / `SESSION_REVIEWER` | **id сессий агентов** |
| `EXECUTOR_MODE` | `relay` \| `deepseek` \| `opencode` |

### 1.3. Замена сессий для болтающих между собой ботов
Агенты — это opencode-сессии. Чтобы подключить своих ботов, нужно подставить
реальные id их сессий.

**Где взять id сессии:** в opencode выполни в сессии агента что-то вроде
показа состояния, либо посмотри в файл состояния/лог opencode
(обычно `ses_xxxxxxxx` + `oc://renderer/server/.../session/`). Также можно
узнать через API: `GET http://127.0.0.1:49300/session` с Basic-авторизацией.

Подставь их **двумя способами** (любой):
- в `.env`: `SESSION_ARCHITECT=ses_...`, `SESSION_EXECUTOR=ses_...`;
- или в `orchestrator/agents_registry.json`:
  ```json
  {
    "architect": "ses_xxxxxxxx",
    "executor":  "ses_yyyyyyyy",
    "reviewer":  "ses_zzzzzzzz"
  }
  ```

Каждый агент уже имеет **свой основной системный промпт** (роль, задачи).
Файлы `orchestrator/prompts/architect.md` и `builder.md` — это **дополнения**
к нему: они описывают только механику работы внутри оркестратора. Приложи
их содержимое к основному промпту агента (добавь в конец), не заменяя его.
В `architect.md` — дополнение для планировщика, в `builder.md` — для
исполнителя; роли там различаются только примерами команд.

## 2. Как агенты общаются друг с другом

Агенты **никогда не пишут друг другу напрямую**. Весь обмен идёт через
оркестратор (он — «почтальон»). Изнутри своей opencode-сессии агент просто
вызывает CLI-команду оркестратора:

```bash
# fire-and-forget: отправить сообщение другому агенту и не ждать
python -m orchestrator send executor "Сделай X по плану Y"

# запрос-ответ: спросить и дождаться ответа
python -m orchestrator ask architect "Какой следующий шаг?"

# сообщить владельцу в Telegram
python -m orchestrator notify "Готов черновик плана"

# запросить апрув у владельца (блокируется до нажатия кнопки)
python -m orchestrator request "Одобрить ли публикацию отчёта?"
```

Оркестратор:
- `send`/`ask` резолвит роль → id сессии (через `agents_registry.json`),
  будит нужную сессию через opencode Server API и передаёт текст;
- `ask` дожидается, пока агент вернётся в статус `idle`, и возвращает ответ
  вызвавшему агенту;
- `notify`/`request` работают с **владельцем** через Telegram.

**Маркировка источника.** Любое сообщение, приходящее в сессию агента,
оркестратор оборачивает заголовком, из которого видно, откуда пришёл запрос:
```
📨 ИСТОЧНИК: Telegram — сообщение от владельца.
🤖 ИСТОЧНИК: другой агент — роль 'architect' (через оркестратор).
⚙️ ИСТОЧНИК: оркестратор (системный шаг).
```
Поэтому агент всегда понимает контекст. Когда агент пишет другому агенту,
он обязан указать свою роль, чтобы получатель увидел источник:
```bash
python -m orchestrator send executor --from architect "Сделай X"
python -m orchestrator ask architect --from executor "<вопрос>"
```
(без `--from` источник помечается как `orchestrator`).

Таким образом «разговор» архитектора с исполнителем — это цепочка
CLI-вызовов, которые оркестратор маршрутизирует между сессиями.

## 3. Папка отчётов `reports/`

Все артефакты агентов (код, планы, `.md`-отчёты) сохраняются в `reports/`
(путь задаётся `REPORTS_DIR`). Когда владелец присылает в Telegram `.md`-файл,
оркестратор тоже складывает его в `reports/` и пересылает агенту.

## 4. Telegram ↔ агенты и поток апрува

### 4.1. Владелец пишет агенту в Telegram
Владелец может написать **любому агенту** прямо в Telegram:
- `/to executor Сделай рефакторинг модуля X`
- либо просто текст — уйдёт агенту по умолчанию (`DEFAULT_AGENT`);
- `@architect покажи план` — маршрутизация по `@роль`.

Оркестратор оборачивает сообщение пометкой 📨 «пришло из Telegram» и
пересылает в сессию агента. Агент **понимает контекст источника** (это описано
в его промпте) и отвечает лаконично, потому что ответ покажут владельцу в
Telegram. Оркестратор пересылает ответ обратно в Telegram.

**Главное меню в Telegram.** У бота есть постоянная клавиатура:
кнопки `✏️ <агент>` (выбор, кому писать), `✅ Апрув` / `❌ Отклонить`
(решение) и `ℹ️ Статус`. Нажми `✏️ executor` — и все следующие сообщения
пойдут этому агенту, пока не выберешь другого. Команды `/to <агент> <вопрос>`
и `@агент ...` тоже работают.

### 4.2. Агент просит апрув у владельца
Если агент вызывает:
```bash
python -m orchestrator request "Одобрить ли удаление базы?"
```
владелец получает в Telegram сообщение с кнопками **✅ Approve / ❌ Reject**
(и, опционально, прикреплённым `.md`-файлом — см. ниже). Команда `request`
**блокируется** до нажатия кнопки и возвращает агенту `'approve'` или
`'reject'`.

> **Важно:** когда это апрув (`request`), агенту **не нужно** отвечать
> текстом в Telegram — владелец просто нажимает кнопку, и решение возвращается
> в сессию агента. Это явно прописано в промптах.

### 4.3. Апрув с прикреплённым `.md`-файлом
Владелец (или агент) может отправить материал на согласование:
- агент: `python -m orchestrator request "@reports/plan.md"` — файл прикрепится
  к Telegram-сообщению владельца вместе с кнопками;
- владелец: присылает в Telegram `.md`-документ с подписью → оркестратор
  кладёт его в `reports/` и пересылает нужному агенту (без апрув-кнопок, это
  уже передача материала агенту).

### 4.4. Автомат оркестратора (`run`)
`python -m orchestrator run` крутит цикл: **architect** формирует план →
**executor** исполняет → **owner-gate** запрашивает апрув у владельца
(кнопки в Telegram). Одобрено — следующий шаг; отклонено — возврат к плану.

## 5. Логика в промптах агентов

Вся схема общения и апрува описана **в самих промптах** (`prompts/architect.md`,
`prompts/builder.md`), которые агенты получают как системный промпт. Там
зафиксировано:

- как вызывать оркестратор (`send`/`ask`/`notify`/`request`);
- что при запросе из Telegram ответ должен быть лаконичным (обёртка 📨);
- что при `request` текстовый ответ в Telegram не нужен — только кнопка;
- что артефакты класть в `reports/`.

Меняя эти промпты, ты меняешь «поведение» агентов, не трогая код.

## 6. Быстрый старт

```bash
cd tg-orchestrator
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # заполнить своими значениями
# заполнить agents_registry.json своими id сессий

# поднять Telegram-бота (релей)
python3 -m orchestrator bot

# или запустить автомат оркестрации
python3 -m orchestrator run
```

Проверки:
```bash
# владелец спрашивает агента
python3 -m orchestrator ask executor "привет, ты на связи?"

# агент (из своей сессии) запрашивает апрув — владелец получит кнопки
python3 -m orchestrator request "Одобрить ли тестовый шаг?"

# статус
python3 -m orchestrator status
```

## 7. Перенос в любой проект

Папка `tg-orchestrator/` самодостаточна: пути резолвятся относительно неё,
`.env` ищется внутри пакета и в корне проекта. Просто скопируй папку к себе,
заполни `.env` + `agents_registry.json`, деплойни `relay_worker.js` в
Cloudflare — и оркестратор готов. Приложи промпты из `prompts/` к системным
промптам своих агентов.
