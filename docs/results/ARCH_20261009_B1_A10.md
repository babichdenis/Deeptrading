# ARCH_20261009 — B1 A10: immutable выгрузка минутных серий и offline DQ

Ревизия 1 (сдача). Задача A10 по DISPATCH (chat.md:1637+): зафиксировать один неизменяемый
набор минутных данных для одинакового входа A7/A9 и дать точный offline DQ. Без PnL,
выбора победителей и оптимизации. **Прибыльность UNKNOWN, holdout NOT_ASSIGNED.**

Принята во внимание приёмка A8 §11: «чистый день» = только ключевые точки, не полный путь;
отсутствующие даты не объявлять неторговыми (calendar NOT_VERIFIED); сессия A7 = [10:00,18:45)
MSK, максимум 525 минут; порогов `open<10` для общего допуска нет; аномалию сохранить.

## 1. Инструмент и режимы

`backend/scripts/day_data_export.py` — два подрежима:
- `export` — READ ONLY выгрузка из настоящей PostgreSQL (.7) в CSV по тикеру + manifest.
- `dq` — offline DQ **только по сохранённым CSV** (без БД), плюс валидация чтения через A7
  `load_minute_csv` (только чтение/парсинг, без `run_ticker`/стратегии).

Никаких writes/DDL/ensure/sync/сети TInvest-MOEX/ботов.

## 4. Offline DQ (по сохранённым CSV)

## 5. Ключевые бары и минуты конфигураций

`dq_coverage.csv` содержит по каждой дате/тикеру явные `yes/no`, причём **различены наличие
минуты и полнота бара** (наличие одной минуты ≠ исполнимый сигнал):

- полные бары: `bar_1000, bar_1020, bar_1030, bar_1200, bar_1400, bar_1820, bar_1830`
  (`yes` = 10 различных минут бакета);
- для каждой конфигурации: `{cfg}_decision_minute_HHMM` (наличие минуты решения),
  `{cfg}_decision_bar_full_HHMM` (полнота 10min-бара решения), `{cfg}_entry_minute_HHMM`
  (наличие минуты входа); cfg = S1-A 12:00/12:10, S1-B 14:00/14:10, S2-A 10:20/10:30,
  S2-B 10:30/10:40;
- время-выход: `time_exit_minute_1830` и `time_exit_bar_full_1830`.

В минутную сетку/полные бары входят **только ts ровно на минутной сетке** (секунды=0 и
микросекунды=0); строка со смещением остаётся в raw/`rows_total`/`dq_issues.csv`, но не делает
минуту/бар присутствующими. Это **описание данных**, не фильтрация входов по будущему. Участки
после возможного входа сохраняются с DQ; будущий replay даст INCOMPLETE, а не удаление сделки.

## 6. Известная аномалия SBER 2026-09-08T12:47Z

Строка присутствует в `csv/SBER.csv` (lineno 98383) и помечена `known_anomaly|zero_volume` в
`dq_issues.csv` — **без автоисправления**. День: 374 сессионных минуты (норма ~525), 24 полных
бара; **отсутствует полный бар `bar_1000`** (10:00), а также `bar_1020`/`bar_1030`. A7 требует
`bar_1000` и для S1, поэтому на этот день **ни одна конфигурация не является полностью готовой**:
у S2-A/S2-B отсутствуют минуты решений/входов 10:20/10:30/10:40; у S1-A/S1-B отдельные точки
(минута 12:00 и её полный бар, минута входа 12:10) присутствуют, но без `bar_1000` конфигурация
не полна. Различать «доступные отдельные точки» и «полную готовность конфигурации»; день по
будущему DQ не удаляется, `volume=0` не объявляется автоматическим запретом.

## 9. Ограничения

- Описательный набор/DQ; прибыльность, издержки, исполнимость и tick не оценивались.
- Календарь MOEX NOT_VERIFIED: ни отсутствующие даты, ни выходные с объёмом не объявляются
  торговыми/неторговыми.
- «Полнота» проверена по внутренним дырам сессии; внешняя истинность источника (БД ↔ биржа)
  не сверялась.
- r1-набор (`20261009T213649Z`) не изменялся; его `dq_*` остаются как историческая ревизия
  (в них `duplicates`/off-minute-сетка считались по старой логике). Действующая DQ-логика и
  все выводы — в r2 (`20261010T103659Z-a10-r2`). Смешивать ревизии нельзя.
- Метаки `*_decision_minute_*` означают наличие минуты, а не исполнимый сигнал;
  полнота бара — отдельная колонка `*_decision_bar_full_*`.
