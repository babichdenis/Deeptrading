## Прогон (один bounded набор, 21 процесс)

- **20 процессов** `<T>__<Cand>__<scen>` (5×2×2), по одному запуску на комбинацию,
  последовательно, **без ретраев-до-успеха**. Каждый: загрузка CSV (hash-check) →
  `CandidateSignalGenerator(Cand, T, warmup_start=2026-06-08).feed(все минуты)` →
  сигналы → `build_ticker_data` один раз → `execute_candidate_signal(signal,
  tdata, CostParams)` на каждый сигнал → ledger A11-формата (manifest/summary/
  trades/skipped/dq). Контракт раннера — `protocol.json:runs.runner_contract`
  (новый `day_candidate_run.py` пишется при имплементации).
- **Лимит 600 с/процесс**: `perl -e 'alarm 600; exec @ARGV'`; превышение =
  `RUN_INCOMPLETE` (сохранить частичное, не успех); ненулевой exit = `RUN_ERROR`
  (stdout/stderr сохранены); ноль сигналов у тикера — легитимный результат.
- **1 отчётный процесс**: `day_research_report.py --run <20> --out report
  --phase development_unvalidated`; отказ репортёра — сохранить причину/входы,
  проверки не ослаблять (A12 §7).

## Сложность (честно)

Генерация: `feed→inspect()` вызывает `build_ticker_data(накопленные минуты)` на
КАЖДУЮ закрытую минуту (строка 281 A18); M≈45 240 session-минут/тикер (87 дней×520)
→ **O(M²) ≈ 1.0e9 шагов на (тикер, кандидат)** ≈ десятки секунд—единицы минут на
процесс на CPython; укладывается в 600 с с запасом ~5–10×. Исполнение —
O(минут дня) на сигнальный день. Итог: полный прогон ~10–40 мин суммарно.
**Быстрый скан не обещается.** Безопасная оптимизация (инкрементальное
поддержание баров/ATR, ребилд только на границах полных баров) — **только
отдельным будущим diff с сохранением prefix-семантики**; принятый A18 сейчас
не меняется.
