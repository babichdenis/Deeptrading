# Работа команды и поддержка знаний

## Начало сессии

1. Прочитать корневой `MEMORY.md`, `AGENTS.md` и [CURRENT_STATE](CURRENT_STATE.md).
2. Открыть тему из [индекса](README.md), затем конкретное назначение и относящиеся к нему новые записи корневого `chat.md`.
3. Сверить абсолютный путь проекта, свою зону файлов, версии входов и ограничения. Архивная инструкция не создаёт новую задачу.

`opencode.json` уже подключает `AGENTS.md` и `MEMORY.md`; конфигурация не менялась. Остальные старые стартовые файлы теперь ведут сюда. Исторические роли My3/DeepSeek не назначают нынешние роли автоматически.

## Независимые ветки

Назначение задаёт вопрос, полный объём до итоговой сдачи, свои файлы, frozen inputs, интерфейс результата, допустимые действия, воспроизведение и критерии приёмки. Не публиковать «задание дано», пока полный текст не записан и не перечитан в chat. Текущие три ветки и зоны — в [PARALLEL-DAY-1](../PARALLEL_DAY_1.md).

Статусы: ASSIGNED → ACK/RUNNING → REVIEW/DELIVERY → ACCEPTED в явном scope либо один сводный REWORK. Отчёт работника без решения архитектора не повышается до ACCEPTED. Внешние работники продолжают свою ветку, не ждут очередного сообщения после каждого шага.

## Запись в chat

Единственный рабочий журнал — корневой `chat.md`. Записи append-only; старые посты не переписываются. `.chat-write.lock` — постоянный обычный файл:

1. Открыть его в режиме append и взять exclusive `fcntl.flock(LOCK_EX)`.
2. Добавить целый пост в chat, выполнить flush/fsync.
3. Проверить фактическое появление своего поста, освободить flock.
4. Не удалять lock-файл и не смешивать flock с mkdir-lock.

В `backend/chat.md` есть историческая переписка; она не заменяет текущий канал. Действующая автоматическая проверка ориентируется на MEMORY и корневой chat; неизменный статус не требует повторных уведомлений владельцу.

## Один владелец каждого типа знания

| Информация | Где обновлять |
|---|---|
| Ограничения работы агента | Корневой AGENTS |
| Быстрый вход новой сессии | MEMORY, без копии всей истории |
| Фактический текущий статус | CURRENT_STATE |
| Очередь этапов | ROADMAP базы знаний |
| Постоянный контракт/архитектура | Тематический файл и соответствующий ADR |
| Назначения и ACK/сдачи/решения | Корневой chat и активный полный пакет |
| Завершённый блок | docs/PROGRESS |
| Результат эксперимента | Неизменяемый run + docs/results, ссылка и scope в RESULTS |

## Как не захламить базу снова

Обновлять существующую тему. Новый файл нужен для самостоятельной темы/контракта, не для каждого сообщения. В статусе указывать дату и источник; после завершения переносить подробности в progress/отчёт. Устаревший вывод явно отзывать или ограничивать областью, не удалять доказательство. Не перезаписывать старые run-артефакты.

Новые документы регистрировать в DOCUMENT_INDEX; каталог содержит также старые адреса и назначения файлов. Архив содержит исходные версии и manifest, а не активные команды. Пути и хэши при переносе проверять; не переносить исполняемые конфигурации или скрипты как часть уборки markdown.
