## 1. Сравнение архитектур ядер (кратко)

| Слой | OsEngine (C#/.NET/WinForms) | Deeptrading (Python/asyncio) | Оценка
|---|---|---|---
| Единица стратегии | `BotPanel`-наследник (класс-панель с Tab'ами) | класс в `engine/strategies.py` + запись в `STRATEGY_REGISTRY` | у них автономнее, у нас компактнее
| Данные стратегии | Tab сам подписывается на серию (`CandleFinishedEvent`) | передаётся список `Candle` в `on_bar`/`run` | у них event-driven live, у нас batch-модель
| Параметры | `Save()/Load()` — робот сам сериализует свои поля в XML | `STRATEGY_CATALOG.params_schema` + JSONB в БД | у них сложнее, но UI сам рисует
| UI параметров | автоматическая генерация контролов из типов полей | ручная вёрстка форм на фронте | **их подход берём** (Фаза D)
| Исполнение | Tab → `ServerMaster` → IServer (реальный/тестовый) | runtime → PaperBroker/LiveBroker (наш код) | паритет, у нас чище
| Режимы | один и тот же BotPanel в live/тестере/оптимизаторе | один и тот же EngineRunner в бэктесте/реплее/live | **паритет по духу** — наш принцип «тест = бот» у них вшит в архитектуру
| Журнал сделок | `Journal` + `Position`-сущности с номерами | `TradeLedger` + `PaperTrade`/`ExperimentTrade` | паритет
| Оптимизация | OsOptimizer: walk-forward, генетика, форвард-фолды | Optuna per-ticker + train/valid-сплит | у них зрелее (берём walk-forward)
| Риск-менеджер | отдельный глобальный `RiskManager` (лимиты на всё приложение) | риск в runtime + gates | у них глобальнее — частично берём

## 2. Плагин-архитектура роботов (то, что понравилось)

### 2.1. Как у них

Робот — это наследник `BotPanel`, регистрируемый в `BotFactory.GetStringNamesOfStrategy()`
(по факту — рефлексивный список всех типов). Каждый робот:
- объявляет свои параметры как обычные поля класса с атрибутами отображения;
- в `Save()/Load()` сам решает, что персистить (сериализация в XML) —
  состояние робота переживает рестарт приложения;
- живёт по циклу событий панели: InitStart/InitEnd → Start/Stop (торговля
  вкл/выкл) → Suppo (период поддержки) — панель сама управляет жизненным циклом;
- создаёт Tab'ы (`CreateSimpleTab()`), подписывается на события, торгует;
- Tab сам шлёт ордера (`SendLimitOrder`/`SendMarketOrder`/`CloseAllOrderToPosition`)
  и активирует стопы (`ActivateStop`/`ActivateProfit`) — SL/TP у них это ордера,
  а не вычисления в коде робота;
- **не знает**, в каком режиме работает: live, тестер или оптимизатор —
  ServerMaster подсовывает нужный IServer (реальный коннектор / TesterServer).

### 2.2. Как у нас сейчас

`STRATEGY_REGISTRY` — плоский словарь `strategy_id → класс`. Стратегия:
- `on_bar(candles) → Signal | None` — чистая функция от окна свечей;
- `validate_params(strategy_id, params)` — валидация границ по `STRATEGY_CATALOG.params_schema`
  (app/engine/catalog.py; карточки StrategyCard: family/wave/правила/ТФ);
- зарегистрирована в одном файле `strategies.py`.

Плюс нашего подхода: стратегии stateless, детерминированы, тестируются golden-тестами.
Минус: нет автономности — робот не управляет своим жизненным циклом,
не может сам открыть несколько серий (разные ТФ), не имеет персистентного состояния.

### 2.3. Что берём (Фаза D)

- **Параметр-схема → автогенерация UI**: у нас уже есть `STRATEGY_CATALOG.params_schema`
  (app/engine/catalog.py — type/min/max/default на каждую из 21 стратегий) — готовый
  источник. Добавляем `GET /api/v1/strategies/{id}/schema` → фронт рисует форму
  автоматически. Параметры перестают требовать ручной вёрстки.
- **Стратегия с несколькими сериями**: после CandleHub (Фаза C) стратегия
  сможет запросить `hub.series(figi, tf)` — как их Tab'ы с разными ТФ.
- **Режим-агностичность**: наш принцип «тест = бот» уже соблюдён;
  закрепляем: новый режим = новый писатель данных в hub, не новая ветка логики.

### 2.4. Сигналы vs ордера — ключевое различие исполнения

| | OsEngine | Deeptrading |
|---|---|---|
| Кто исполняет | робот сам: Tab → ордера | стратегия → Signal, исполнение в EngineRunner |
| SL/TP | стоп-ОРДЕРА (ActivateStop/ActivateProfit) | расчёт выхода в runtime (EOD/политики/гейты) |
| Состояние | mutable, персистится Save/Load, переживает рестарт | stateless, детерминизм + golden-тесты |
| Падение процесса | стопы остаются у коннектора/брокера | позиции без защиты |

Вывод: нашу модель сохраняем (тестируемость и воспроизводимость важнее),
но для live (Фаза E) — страховочный server-side SL на каждую открытую позицию:
сейчас падение бота = незащищённая позиция.

## 3. Режимы: live / test / optimize — параллель

| | OsEngine | Deeptrading | Действие
|---|---|---|---
| Live | BotPanel + реальный Server | runtime + CandleFeed + LiveBroker/PaperBroker | —
| Test (реплей) | BotPanel + TesterServer (сеть Tape'ов) | runtime + ReplayFeed из БД | наш реплей проще, оставляем
| Оптимизация | OsOptimizer: клон ботов × параметры × форвард-фолды | Optuna per-ticker (train/valid) | **берём walk-forward-фолды**
| Прогон результатов | Journal + бэктест-отчёты | `bot_test_runs` + golden-отчёты | паритет

Ключевой вывод: у них режим = подмена источника данных + исполнения при
НЕИЗМЕННОМ коде робота. У нас так же (писатели feed/replay → runtime),
но пока это склеено руками внутри `runtime.py` (~5.7k строк). CandleHub
(Фаза C) формализует границу: писатели кормят hub, runtime подписан на hub.

## 4. Walk-forward (чего нам не хватает)

OsOptimizer умеет: разбить историю на фолды (train/forward),
прогнать оптимизацию на train, проверить на forward, усреднить.

Наш аналог: Optuna per-ticker уже делит train/valid, но фолдов несколько
и выборка фиксирована. Предложение (Фаза D/E):
- `scripts/walk_forward.py`: N фолдов (например, 4×[2 мес train / 2 нед forward]);
- на каждом фолде — Optuna (уже есть), метрики только на forward;
- итог = медиана forward-метрик по фолдам → честная OOS-оценка;
- реестр результатов — в `instruments.optuna_params` с пометкой фолда.

## 5. RiskManager глобальный (частично берём)

У них: RiskManager — глобальный синглтон поверх всех панелей:
- лимит просадки дня (останавливает всё приложение);
- лимит сделок в день; лимит объёма позиции; чёрные списки.

У нас: риск размазан (runtime-гейты, session-risk, imoex_guard, portfolio.py).
Предложение: не переносить их UI-синглтон, а собрать `app/bot/risk_limits.py` —
сводные дневные лимиты (max DD%, max trades, max volume), проверяемые
в runtime до отправки ордера. Приоритет — после Фазы C.
