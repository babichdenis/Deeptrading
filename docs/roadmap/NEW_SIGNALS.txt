Проверил именно текущую реализацию. И здесь уже видно, **почему я бы не внедрял предложенный тобой `M1 × M5 × M10 × 10 функций` напрямую**.

### Что сейчас реально происходит

У тебя `EnsembleV4Strategy.on_bar()` вызывается **на каждом 1m баре**, это прямо зафиксировано в коде. При этом `compute_ensemble()` вызывается каждый раз после проверки режима.  

То есть при 30 акциях у тебя потенциально:

```text
30 акций
× 1 раз / минуту
× compute_ensemble()
```

И это намного важнее, чем кажется.

Причём `compute_ensemble()` получает **весь массив `candles`**, а не только новый бар:

```python
res = compute_ensemble(list(candles), req)
```

То есть если `candles` содержит, например, несколько сотен M1 свечей, функция потенциально каждый раз заново работает с историей.

```python

SELL = -1
NONE = 0
```

Я бы перешёл к силе сигнала:

```python
@dataclass
class Signal:

    strength: float    # 0..1
    reason: str
```

Например:

```text

```

Тогда ансамбль считает не просто:

```python

```

а:

```python
weighted_score = sum(signal.side * signal.strength * weight)
```

Это намного информативнее.

# 3. Разделить `setup` и `trigger`

Это, на мой взгляд, самое важное изменение.

Например:

### Setup

M5 показывает:

```text
RSI вышел из oversold
+
цена вернулась выше VWAP
+
MACD histogram растёт
```

Это означает:

> потенциально хороший LONG-контекст

Но **это ещё не вход**.

### Trigger

На M1:

```text
close > high предыдущей свечи
+
volume > average volume
+
цена не слишком далеко от VWAP
```

И только здесь:

```python
ENTER_LONG
```

Получается:

```text
SETUP → CONFIRMATION → TRIGGER → ENTRY
```

Это обычно гораздо полезнее, чем пытаться заставить все индикаторы одновременно дать BUY.

# 13. Конкретная схема, которую я бы тестировал

Я бы сделал первую версию примерно такой:

```python

    if state.m10_direction != BUY:
        return None

    # 2. Regime
    if state.regime not in (
        TREND_UP,
        NEUTRAL,

        return None

    if state.m5_setup_score < 0.60:

    if state.m5_score < 0.0:

    if not state.m1_trigger:
        return None

    # 6. Final quality
    score = (
        0.35 * state.regime_score +
        0.35 * state.m5_setup_score +
        0.20 * state.m1_trigger_score +
        0.10 * state.volume_score
    )

    if score < 0.70:
        return None

    return EntrySignal(
        side=BUY,
        score=score,
    )
```

А выход:

```python
def detect_exit(position, state):

    if state.hard_stop:
        return "STOP"

    if state.take_profit:
        return "TP"

    if state.trailing_stop:
        return "TRAIL"

    if state.regime_failed:
        return "REGIME"

    if state.momentum_score < 0.45:
        return "MOMENTUM"

    if state.entry_score - state.entry_score_peak < -0.25:
        return "DETERIORATION"

    return None
```

| Приоритет | Изменение                             | Зачем                                    |
| --------- | ------------------------------------- | ---------------------------------------- |
| **1**     | M10 → M5 → M1                         | убрать шум                               |
| **2**     | Setup отдельно от Trigger             | повысить качество момента входа          |
| **3**     | Weighted score вместо простого quorum | учитывать силу сигналов                  |
| **4**     | `BUY - SELL` edge                     | отсеять конфликтующие сигналы            |

| **6**     | отдельная exit-модель                 | лучше фиксировать окончание движения     |
| **7**     | deterioration exit                    | раньше ловить потерю импульса            |
| **8**     | hysteresis                            | уменьшить flip-flop                      |
| **9**     | incremental indicators/cache          | резко снизить CPU                        |
| **10**    | adaptive quorum                       | только после проверки базовой версии     |

**Я бы пока вообще не делал 30 голосов.** Сначала выжал бы максимум из твоих существующих 7 V2 setup'ов через `M10 context → M5 setup → M1 trigger`. Это даст гораздо более чистый эксперимент и позволит понять, **какая именно часть детектора реально улучшает сделки**.

И самое важное: не ориентироваться только на `win rate`. Для каждой версии сравнивать минимум **expectancy, PF, max DD, среднюю прибыль/убыток, количество сделок и PnL после комиссии/проскальзывания** на out-of-sample периоде.





Да. Для твоего случая я бы строил оптимизацию **не как один огромный Optuna-поиск**, а как последовательность экспериментов: сначала определить устойчивые параметры каждой функции, затем совместимость функций, затем веса, затем пороги ансамбля, и только в самом конце — совместно оптимизировать небольшое число наиболее важных параметров.

Главная цель — получить не «максимум PnL на истории», а **устойчивую конфигурацию, которая сохраняет преимущество на невидимых данных**.

## 0. Сначала зафиксировать экспериментальную среду

Для каждого прогона неизменными должны быть:

* размер позиции;

# 15. Очень важный принцип Optuna: оптимизировать не PnL

Я бы сделал objective примерно:

```python
    PF
    + alpha * expectancy
    + beta * Sharpe
    - gamma * max_drawdown
    - penalty_for_low_trade_count
```

Но ещё лучше использовать **несколько objectives**.

```text

    Net Profit

    Sharpe
```

Получишь Pareto frontier вместо одного искусственного «лучшего» решения.

# 1. Что должен делать regime detector

Он **не должен говорить "BUY" или "SELL"**.

Он должен говорить:

```python
regime = {
    "trend": "UP",
    "volatility": "NORMAL",
    "confidence": 0.82
}
```

Или твои четыре состояния:

```text
NEUTRAL
TREND_UP
TREND_DOWN
HIGH_VOLATILITY
```

Но тут есть важный нюанс: **волатильность — это не совсем тот же тип измерения, что направление**.

Лучше концептуально разделить:

```text
REGIME
├── direction
│   ├── UP
│   ├── DOWN
│   └── NEUTRAL
│
└── volatility
    ├── LOW
    ├── NORMAL
    └── HIGH
```

Тогда возможна ситуация:

```text
TREND_UP + HIGH_VOLATILITY
TREND_UP + LOW_VOLATILITY
NEUTRAL + HIGH_VOLATILITY
NEUTRAL + LOW_VOLATILITY
```

Это намного информативнее.

# 2. Не оптимизируй regime detector вместе с ансамблем

Это очень важный момент для твоего Optuna-плана.

Сначала:

# 3. Как использовать режимы для разных функций

Вот здесь начинается самое интересное.

Твои setup'ы логически делятся на две группы.

### Trend-following

```text
MACD
Donchian
Pullback
breakout
momentum
```

### Mean-reversion

```text
RSI reversal
Bollinger reclaim
VWAP reclaim
```

Поэтому режим может **менять веса setup'ов**.

Например:

### TREND_UP

```text
MACD       weight 1.0
Donchian   weight 1.0
Pullback   weight 0.9
VWAP       weight 0.7
RSI        weight 0.3
Bollinger  weight 0.2
```

Не потому, что эти цифры заранее правильные — **это search space для Optuna**.

---

### NEUTRAL

Например:

```text
RSI        1.0
Bollinger  1.0
VWAP       0.9
MACD       0.3
Donchian   0.2
Pullback   0.4
```

---

### TREND_DOWN

Для LONG-only стратегии особенно интересно:

```text
MACD       0.2
Donchian   0.1
Pullback   0.2
RSI        0.5
VWAP       0.4
Bollinger  0.4
```

И часть setup'ов вообще может быть запрещена.

---

### HIGH_VOLATILITY

Я бы не делал автоматически:

```text
HIGH_VOLATILITY → разрешить всё
```

Скорее:

```text
HIGH_VOLATILITY
       ↓
проверить качество движения
       ↓
либо breakout
либо skip
```

Потому что высокая волатильность может быть как хорошим breakout, так и просто хаосом.

# 5. Ещё лучше — regime как prior

Я бы не делал жёсткое:

```python
if TREND_UP:
    RSI = disabled
```

Потому что это может быть слишком грубо.

Лучше:

```python
final_weight = base_weight * regime_multiplier
```

Например:

```text
RSI:
base_weight = 0.8

TREND_UP:
multiplier = 0.4

итог:
0.8 × 0.4 = 0.32
```

А MACD:

```text
base_weight = 0.8
TREND_UP multiplier = 1.4

итог = 1.12
```

Так режим **смещает вероятность**, а не диктует результат.

# 6. И это прекрасно ложится на Optuna

Ты можешь разделить оптимизацию на два уровня.

### Stage A

Оптимизируем базовые веса:

```text
w_RSI
w_BB
w_VWAP
w_MACD
w_DONCHIAN
w_PULLBACK
```

### Stage B

Оптимизируем regime multipliers:

```text
TREND_UP:
    RSI_mult
    BB_mult
    VWAP_mult
    MACD_mult
    ...

NEUTRAL:
    RSI_mult
    BB_mult
    ...

HIGH_VOL:
    ...
```

Но **не сразу все multipliers**.

Сначала только 2–3 наиболее важных.

Например:

```text
TREND_UP:
    trend_setup_multiplier
    mean_reversion_multiplier

NEUTRAL:
    trend_setup_multiplier
    mean_reversion_multiplier
```

И только если это показывает стабильное улучшение — расширять.

# 10. Потом возникает очень важный вопрос: нужен ли вообще отдельный набор параметров?

Допустим Optuna показывает:

```text

NEUTRAL:
RSI period 14–17
```

Тогда нет смысла иметь:


Можно оставить:

```text

```

Это **лучше для устойчивости**.

А вот если:

```text

NEUTRAL: 7–11
```

тогда режим-зависимый параметр действительно может быть оправдан.

# 11. Поэтому введи "complexity penalty"

При сравнении двух конфигураций:

```text
A:
20 параметров

B:
8 параметров
```

если они показывают практически одинаковый validation result, я бы предпочёл **более простую** конфигурацию.

В objective можно добавить штраф:

```python
score = performance - complexity_penalty
```

где:

```python
complexity_penalty = k * number_of_active_parameters
```

Не обязательно буквально делать это сразу в формуле — можно использовать как критерий отбора Pareto-решений.

# 12. Как использовать HIGH_VOLATILITY

Вот здесь я бы был особенно осторожен.

Не стоит делать:

```text
HIGH_VOLATILITY → lower quorum
```

автоматически.

Я бы разделил:

```text
HIGH_VOLATILITY
        │
        ├── directional expansion
        │       ↓
        │    breakout
        │
        └── chaotic expansion
                ↓
               SKIP
```

То есть нужен второй фильтр:

```text
volatility
+
directional efficiency
```

Например можно измерять:

```text
abs(price_change)
-----------------
true_range
```

Если рынок сильно ходит, но почти никуда не продвигается:

```text
high volatility
+
low directional efficiency
=
SKIP
```

Это потенциально очень полезный фильтр именно для твоей проблемы с ложными входами.

# 1. Самые интересные кандидаты для исследования

Я бы поставил в следующий экспериментальный пакет всего **5 гейтов**:

### A. `entry_h1_align`

Это один из наиболее осмысленных кандидатов:

```python
if ctx.h1_side != ctx.side:
    reject
```

То есть:

**BUY → H1 должен быть BUY**

**SELL → H1 должен быть SELL**

У вас REF уже жил с `entry_h1_align=true`, поэтому здесь особенно важно не «улучшить» его вслепую, а проверить:

```text
REF
REF - H1 align
REF + более строгий H1 threshold
REF + более мягкий H1 threshold
```

Потому что сам факт, что H1 MACD имеет сторону, ещё не означает сильный сигнал.

# 2. `tf_conflict` — интереснее, чем просто H1 veto

Сейчас:

```python
daily bias = UP
H1 = SELL
→ reject
```

Это фактически **conflict detector**.

Но здесь есть потенциальная проблема: если дневной bias и H1 действительно расходятся в переходной фазе рынка, именно там могут возникать хорошие reversal-сделки.

Поэтому я бы не делал его автоматически жёстче.

Исследовать:

```text
A: current
B: выключен
C: reject только если disagreement сильный
```

То есть вместо бинарного:

```python
daily != H1
```

потом можно перейти к:

```text
|daily_strength| > X
AND
|h1_strength| > Y
AND
directions conflict
```

Это гораздо интереснее.

# 5. `liquidity_check`

Сейчас:

```python
entry_min_turnover = 0
```

Я бы **не включал его сразу с фиксированным ₽-порогом**.

Причина прямо видна из кода:

```python

```

Абсолютный оборот плохо нормализован между инструментами.

Например, условные 1 млн ₽ для одного тикера могут быть огромным фильтром, а для другого — практически ничего.

Лучше будущая версия:

```text

/
median turnover instrument
```

или:

```text
current bar turnover
/
rolling median bar turnover
```

То есть **relative liquidity**, а не абсолютные ₽.

# 7. `loss_streak_hold` — очень спорный alpha-гейт

Вот это:

```text
2 losses → HOLD 60 min
```

я бы **не воспринимал как доказанный защитный механизм**.

Потому что после двух убытков могут происходить два совершенно разных сценария:

### Сценарий A

Рынок действительно поменялся → пауза полезна.

### Сценарий B

Стратегия получила случайную серию убытков → следующий сигнал имеет обычное ожидание.

Во втором случае loss-streak просто пропускает хорошие сделки.

Поэтому исследовать надо против:

```text
OFF
1 loss
2 losses
3 losses
```

и отдельно:

```text
hold 30
60
90
120 min
```

Но **не оптимизировать сразу оба параметра**.

# 8. Beta / clusters / sectors

Здесь я бы пока **ничего не включал**.

Почему?

Потому что это не signal-quality filters. Это **portfolio construction**.

Например:

```python

```

может отклонить хороший сигнал только потому, что уже есть другие high-beta позиции.

Это может уменьшить portfolio DD, но не улучшить alpha конкретного сигнала.

Поэтому их надо тестировать на другом уровне:

```text
Signal quality
        ↓
Portfolio construction
        ↓
Risk
```

И отдельно измерять:

```text
signal expectancy
portfolio DD
correlation
concentration
```


Это уже не просто gate.

Это **механизм изменения исполнения и приоритетов**.

Поэтому для исследования стратегии:

```text
queue = OFF
```

А потом отдельный эксперимент:

```text
REF
REF + queue
REF + top boost
REF + relax caps
```

Иначе становится трудно понять, что именно улучшило результат.

# 10. Есть архитектурная проблема с `GATES`

Вот это я бы исправил **до дальнейшей оптимизации**.

Реестр говорит:

```python
GateSpec("risk_limit", ...)
```

но функция:

```python
gate_risk_day()
```

возвращает:

```python
f"risk_{str(ctx.risk_state).lower()}"
```

Например:

```text
risk_warning
risk_stop
```

а не:

```text
risk_limit
```

Значит:

**реестр и `skip_counts` могут расходиться.**

То же самое надо проверить по всем динамическим reason codes.

Это важно для экспериментов: иначе вы можете решить, что какой-то gate почти никогда не срабатывает, хотя его reject-коды просто записываются под другим именем.

# 11. Ещё одна важная проблема: `orderbook_error`

Сейчас:

```python
if ctx.orderbook is None:
    return False, "orderbook_error"
```

То есть:

> если стакан не получили → торговля запрещена.

Это **fail-closed**.

Для безопасности это нормально.

Но для research это опасно: недоступность стакана становится одновременно:

**data-quality filter + trading filter.**

Нужно разделить:

```text
orderbook_reject
orderbook_unavailable
```

И статистику вести отдельно.

Иначе можно ошибочно решить:

> «orderbook gate улучшил стратегию»

хотя на самом деле он просто не торговал в периоды проблем с данными.

### И главное

Не надо выбирать gate по принципу:

> «Net вырос → включаем».

Например:

```text
REF:       +4000, 500 trades
Gate A:    +4300, 350 trades
```

Это ещё не означает, что A лучше. Он мог просто убрать 150 плохих **и одновременно случайно убрать будущие хорошие сделки**.

Поэтому я бы ввёл для каждого gate ещё два показателя:

```text
signal rejection rate
retained expectancy
```

и обязательно смотреть **какие сделки он отбрасывает**, а не только конечный PnL.
