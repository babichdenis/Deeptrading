# DEV_PLAN — Развитие бота: единый движок + скорость (2026-09-06)

> **Проблема:** 3 расходящиеся реализации движка + 71с на 1 прогон месяца (1 тикер).
> **Цель:** единый движок для live/backtest + 10-30x ускорение Python-оптимизациями БЕЗ Rust.

---

## 1. Диагноз (профиль compute_ensemble, август, SMLT, 28k свечей, 7 стратегий)

| Компонент | Время (71с всего) | % | Причина |
|-----------|-------------------|----|---------|
| `_signal_quality` (ensemble.py:252) | ~38с | 54% | 13M lambda `min()`/`abs()`, O(сигналы × окно) |
| `runner.run → plan_entry → atr()` | ~14с | 20% | ATR пересчитывается на КАЖДЫЙ вход O(входы × N) |
| `_oracle_coverage` | ~13с | 18% | zigzag-аналитика (не нужна для решений) |
| `_counterfactual_*` | ~2с | 3% | аналитика |
| `generate_signals` (7 стратегий) | ~3с | 4% | **уже быстро** |

**Ключевые выводы:**
1. `generate_signals`/индикаторы — НЕ bottleneck (4%). Rust-раздел DeepEngine.txt про rsi/atr/macd бьёт мимо.
2. Убийцы — O(N²) паттерны в Python + 20M вызовов `total_seconds()` на datetime.
3. Потенциал: **10-30×** простыми правками Python. Rust не нужен (пока).
4. Портфельный режим (merged timeline, 20 тикеров одновременно) — отдельный контур, не per-ticker.

## 4. Живой мониторинг и hot-path runtime (аудит 2026-09-10)

### Замечания из аудита
1. **Регрессия `bias_tf_sec` (обыграна 2026-09-10):** коммит `4a295d0` заменил `// 3600` на `// bias_tf_sec` внутри `_run_pipeline`, но параметр в сигнатуру не передали → каждый `compute_ensemble` падал с `NameError`, а `on_bar` глотил через `except Exception: return None`. **Бот не торговал молча.** Фикс: параметр `bias_tf_sec: int = 3600` в `_run_pipeline` + передача из `compute_ensemble`.
2. **`asyncpg NOT IN :list` (починено):** `_hot_add_universe` падал с `PostgresSyntaxError`, `except: pass` глотал → hot_adds=0, SBER/T висели в pending. Фикс: `NOT (figi = ANY(:skip))` + логирование `last_error`.
3. **Паттерн «тихого сбоя»:** в боте слишком много `except Exception: pass`/`return None`. Любая ошибка в стратегии = «бот работает, но не торгует». Нужен механизм, который видит аномалии сразу (это и есть `_metrics_loop`).
4. **CPU живого бота:** `compute_ensemble` на 4320 барах 1m = **700–1400 ms/тикер**, гоняется на КАЖДОМ 5м-закрытии (22 тикера). `list(buffer)` копируется на каждый бар (22×/мин ~95k объектов/мин). `broker.get_position()` на каждую свечу НЕ дора — кэш портфеля TTL 15с спасает. Нагрузка на .3 (load 31-39) — это Yandex/WindowServer/VM, НЕ наш движок (uvicorn ~0-18%).
5. **Оптимизации (потенциал):**
   - кэшировать `compute_ensemble` между 5м-закрытиями (инкрементальный пересчёт или пропуск `_signal_quality` в live — это аналитика, не решения);
   - НЕ копировать `list(buffer)` на каждый тикер — в `on_bar` отдавать slice/ссылку (но осторожно: стратегия мутирует? нет);
   - `_oracle_coverage`/`_counterfactual_*` — в live не нужны (флаг).

### Система метрик `_metrics_loop` (добавлена 2026-09-10)
- Каждые 30с пишет в `status['metrics']`: `candles_per_sec`, `bar_ms_avg/max`, `ensemble_ms_avg/max`, `persist_ms_avg`, `persist_q/q5`, size universe, кол-во сигналов.
- Реакция на аномалии (alert + events.log + _log):
  - нет свечей >90с в торговую сессию;
  - очередь персиста почти полна (>1900);
  - ensemble avg >2000ms;
  - bar avg >500ms.
- Сброс метрик при `start()`, поле `metrics` в GET /api/v1/bot/status.

### Правила для будущих правок
- **Никогда** не глотать исключения молча в hot-path бота: минимум `self._log`/`events.log`, лучше метрика.
- Любой запрос к БД/брокеру в `_process_candle` — только через кэш/очередь.
- После любых правок бота прогонять: `curl /api/v1/bot/status` → `running=true` + `metrics` растут, `signals_seen` растёт на 5м-закрытиях.

## 5. Критерии "не упираться в тормоза"

- 1 прогон месяца 1 тикера: 71с → **<5с** (Шаг 1)
- Ночная Optuna 5-7 акций × 60 trials × месяц: ~60 мин → **<10 мин**
- Портфельный прогон 20 акций merged: **<2 мин** (иначе портфельная Optuna невозможна)

## 6. Риски и правила

1. **Детерминизм:** после каждого изменения в compute_ensemble/runtime — прогон golden-тестов + сравнение сделок ДО/ПОСЛЕ. Не менять поведение, только скорость.
2. **Паритет live = backtest** — уже достигнут, не сломать (см. ENGINE_ARCHITECTURE §10).
3. **Не переписывать бизнес-логику на Rust** — только CPU-bound горячие пути, если Шаг 1 не даст нужной скорости.
4. Порядок жёсткий: Шаг 1 → Шаг 2 → Шаг 3. Не начинать стримы/Rust до ускорения.
