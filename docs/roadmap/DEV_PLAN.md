# DEV_PLAN — Развитие бота: единый движок + скорость (2026-09-06)

> **Проблема:** 3 расходящиеся реализации движка + 71с на 1 прогон месяца (1 тикер).
> **Цель:** единый движок для live/backtest + 10-30x ускорение Python-оптимизациями БЕЗ Rust.

---

## 1. Диагноз (профиль compute_ensemble, август, SMLT, 28k свечей, 7 стратегий)

| Компонент | Время (71с всего) | % | Причина |
|-----------|-------------------|----|---------|
| `_signal_quality` (ensemble.py:252) | ~38с | 54% | 13M lambda `min()`/`abs()`, O(сигналы × окно) |
| `runner.run → plan_entry → atr()` | ~14с | 20% | ATR пересчитывается на КАЖДЫЙ вход O(входы × N) |
| `_oracle_coverage` | ~13с | 18% | zigzag-аналитика (не нужна для решений) |
| `_counterfactual_*` | ~2с | 3% | аналитика |
| `generate_signals` (7 стратегий) | ~3с | 4% | **уже быстро** |

**Ключевые выводы:**
1. `generate_signals`/индикаторы — НЕ bottleneck (4%). Rust-раздел DeepEngine.txt про rsi/atr/macd бьёт мимо.
2. Убийцы — O(N²) паттерны в Python + 20M вызовов `total_seconds()` на datetime.
3. Потенциал: **10-30×** простыми правками Python. Rust не нужен (пока).
4. Портфельный режим (merged timeline, 20 тикеров одновременно) — отдельный контур, не per-ticker.

## 3. План работ по шагам

### Шаг 1. Ускорение compute_ensemble (10-30×) — ~1 день
**Приоритет: сделать ПЕРЕД всем остальным** — от этого зависит скорость всех тестов/Optuna/портфеля.

1. **`_signal_quality` (54% времени):** убрать lambda `min/abs` → векторизовать или кэшировать окна. Замер до/после.
2. **Кэш ATR в `plan_entry`:** ATR не зависит от входа — считать 1 раз на серию, не на каждый из 211 входов. (Аналог `_get_5m_bars()` уже сделан в runtime.py.)
3. **int-таймстампы вместо datetime:** заменить 20M `total_seconds()` на epoch int в hot path.
4. `_oracle_coverage` и `_counterfactual_*` — вынести за флаг (нужны только для аналитики, не для сделок).

**Проверка:** golden-тесты + детерминизм (те же сделки до/после). Цель: 71с → 3-7с.

### Шаг 2. Инъекция в runtime.py — единый движок для self-test (~полдня)
Сделать `PaperBotRuntime` запускаемым на истории БЕЗ токена Тинивеста:
- `start(cfg, broker=None, feed=None, stream_manager=None)` — инъекции
- Подставить `ReplayBroker` (интерфейс как PaperBroker) + `ReplayFeed` (свечи из БД по merged timeline)
- stream_manager = None (или mock)

**Выгода:** вносим правку в runtime → гоняем на истории → видим ошибку. Self-test движка. Исчезает дублирование с backtest_full_bot.py (удалить его).

### Шаг 3. Портфельный бэктестер (merged timeline) — для оптимизации портфеля
Единый прогон на 20 акций с ОБЩИМ пулом капитала + одновременные позиции. На базе Шага 1 (быстрый) + Шага 2 (единая логика).
Это блокер для: allocation (сколько на акцию), выбор 5-7 из 20, leverage.

### Шаг 4. Ночная Optuna (после Шага 1)
- Скорость: 20 тикеров × месяц × 60 trials станет реальной (сейчас 71с → 3с = 20× быстрее = ~3 мин на тикер)
- Параметры из `optuna_sweep_params.py` уже готовы

### Шаг 5. Стримы (Sreaming.md) — только после 1-3
Сначала убрать O(N²) (Шаг 1) — тогда "стриминг" сводится к мемоизации, а не к переписыванию на инкрементальные индикаторы.

### Шаг 6. Rust/C (DeepEngine.txt) — ОТЛОЖЕНО
После Шага 1 (10-30×) пересмотреть. Если нужно ещё — только top-1 по новому профилю, с Python-fallback.

## 4. Критерии "не упираться в тормоза"

- 1 прогон месяца 1 тикера: 71с → **<5с** (Шаг 1)
- Ночная Optuna 5-7 акций × 60 trials × месяц: ~60 мин → **<10 мин**
- Портфельный прогон 20 акций merged: **<2 мин** (иначе портфельная Optuna невозможна)

## 5. Риски и правила

1. **Детерминизм:** после каждого изменения в compute_ensemble/runtime — прогон golden-тестов + сравнение сделок ДО/ПОСЛЕ. Не менять поведение, только скорость.
2. **Паритет live = backtest** — уже достигнут, не сломать (см. ENGINE_ARCHITECTURE §10).
3. **Не переписывать бизнес-логику на Rust** — только CPU-bound горячие пути, если Шаг 1 не даст нужной скорости.
4. Порядок жёсткий: Шаг 1 → Шаг 2 → Шаг 3. Не начинать стримы/Rust до ускорения.
